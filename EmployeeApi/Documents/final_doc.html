1. The Complete System

This project is an HTTP API. It receives a request, validates and authorizes it, executes application logic, reads or writes SQL Server data, and returns an HTTP response. A React page can display that response. Postman can call the same endpoints without any page.

React form / Postman
  -> HTTP request: method + URL + headers + JSON
  -> JWT authentication and role authorization
  -> Controller action + request ViewModel
  -> Service interface resolved to a service object
  -> Dapper procedure call OR EF Core query
  -> SQL Server
  -> C# result object
  -> Controller HTTP result
  -> JSON response
  -> Frontend state -> rendered UI

A controller knows about HTTP: route parameters, status codes, and request bodies. A service knows how to obtain and persist domain data. The model represents the stored data. A ViewModel defines what the API accepts or returns. Keeping these responsibilities separate makes the flow easier to test and change.

There is no Razor View in this flow

Interface versus implementation

IEmployeeService is a contract: it lists methods and their result types. EmployeeService supplies the method bodies. A controller asks for the interface in its constructor. Dependency injection chooses the implementation registered in the service container. You do not call the interface and implementation separately; the interface reference points to an implementation object.

IEmployeeService service = an EmployeeService instance;
await service.GetById(5);
// Executes EmployeeService.GetById(5).

Entity, table row, and JSON are different things

An Employee object lives in application memory. A row lives in SQL Server. Dapper can map a result row into the object. A JSON serializer can later turn selected object properties into a response. Attributes such as JsonIgnore affect serialization; they do not remove the corresponding column from SQL Server.

Routing and construction

ApiController enables API binding and validation conventions. Route gives the common URL prefix. ControllerBase provides Ok, NotFound, Unauthorized, NoContent, and CreatedAtAction helpers. The constructor stores injected service references so actions can call them.

[HttpGet("{id:int}")] matches a numeric route segment, such as /api/employee/12. The route value is bound to int id. It does not prove that row 12 exists.

Get: list employees

  1. The role attribute permits Manager or Employee.
  2. GetAll returns an asynchronous list from the employee service.
  3. Ok wraps the list in HTTP 200. An empty list is a successful result, normally serialized as [] rather than 404.

There is no current-user filter in this action or in the C# GetAll method. Role access is not the same as permission to read only one's own row. Salary and other public entity properties are included in the response; only PasswordHash is explicitly hidden.

GetById: one employee

The service returns either an Employee object or null. The conditional return chooses 404 for null and 200 for an object. Any employee allowed by the role attribute can request any numeric ID; no employee-ownership comparison is present.

Create: request to saved account

  1. [HttpPost("new")] makes the URL /api/employee/new. The Manager role is required.
  2. [FromBody] CreateEmployeeViewModel model receives validated JSON values.
  3. new EmployeeEntity { ... } maps allowed profile fields from the request into an entity. Id is left for SQL Server to generate.
  4. new PasswordHasher<EmployeeEntity>() creates the framework password hashing helper.
  5. HashPassword(employee, model.Password) produces an encoded salted hash. The raw password is not assigned to a database entity property.
  6. employee.Role = model.Role selects the stored role from the authorized Manager's request. The current ViewModel does not restrict its values to an allowlist.
  7. await _service.Create(employee) sends entity values, including PasswordHash, to dbo.CreateEmployee and receives the inserted row.
  8. SendAccountCreatedAsync(createdEmployee, model.Password) sends the welcome email using the original password still available in the request.
  9. CreatedAtAction(nameof(GetById), ...) produces HTTP 201, a body containing the created employee, and a Location header pointing to its GET URL. It does not execute GetById and does not redirect the frontend to a dashboard.
Two separate side effects: the row is saved before email is sent. There is no transaction spanning SQL and SMTP, and no catch here for SMTP failure. If SMTP throws, the request can fail with 500 even though the employee exists. Check for that row before retrying creation.

Update: what changes and what stays

  1. The Manager calls PUT /api/employee/{id} with the update body.
  2. The action first loads the existing employee. Missing data returns 404 before any update.
  3. A new entity is built with Id from the URL and the profile values from the body.
  4. PasswordHash and Role are copied from existingEmployee. This avoids replacing them with empty defaults, but also means model.Password and model.Role have no effect.
  5. The service passes all mapped values to dbo.UpdateEmployee. The result is returned with 200.

To later support a password or role change, the edit location is this mapping block: validate the role against allowed values, hash a supplied nonblank password, and preserve existing values when not changing them. A self-service password change would need its own authorized contract and current-password check. That feature is not implemented by the existing optional properties.

A row can disappear between the existence check and the update. The service then throws KeyNotFoundException, which this action does not catch. The preliminary check does not make the operation atomic.

Delete: bool to HTTP status

The Manager calls DELETE /api/employee/{id}. The service returns true when the procedure's scalar deletion count is greater than zero. True becomes 204 with no response body; false becomes 404. SQL exceptions still propagate; false does not mean every possible SQL failure was handled.

Constructor, connection, and parameter mapping

The constructor reads DefaultConnection once and stores it in _connString. A missing connection string throws a configuration error. Each operation constructs a SqlConnection. Dapper's asynchronous APIs open a closed connection as needed for execution; the using declaration ensures disposal afterward. You can explicitly OpenAsync, but its absence here is not the cause of a missing-procedure error.

CommandType.StoredProcedure tells SQL Server that the command text is a procedure name. It does not create or deploy that procedure. The procedure must already exist in the schema and database selected by this connection, and the application's SQL identity must have execution permission.

In new { Email = email }, Email is the parameter name and email is the C# value. In new { employee.Name }, C# infers a property named Name containing employee.Name. Dapper sends values as parameters rather than concatenating them into SQL text.

Why the SQL result matters

Dapper maps matching column names into properties. A result column called Name populates Employee.Name. It does not know that an unrelated column named FullName should populate Name unless the query aliases it appropriately. Missing columns can leave default property values and cause subtle errors.

If GetById omits PasswordHash, the entity defaults that property to an empty string. The current update action then copies that empty string and could overwrite the stored hash. If Role is omitted, the default Employee role could replace a Manager role. Query shape is part of the application contract, even when SQL compiles successfully.

ExecuteScalar reads a selected value; ExecuteAsync reports affected-row counts through a different mechanism. They are not interchangeable. SQL RETURN is a procedure return code, not the SELECT result consumed by ExecuteScalar here. An extra diagnostic SELECT before the intended result can break mapping.

Dapper and EF Core together

Dapper offers direct control over the command and result mapping. EF Core offers model-aware queries and change tracking. The project uses both. Switching a service to Dapper does not remove the need for schema deployment, replace the DbContext in other services, or make SQL Server generate procedures automatically.

8. SQL Stored Procedures Explained

A stored procedure is named SQL code saved inside a SQL Server database. C# calls that name with parameters. SQL Server executes its body and sends result sets or output values back. Storing a procedure in SSMS's editor is not enough: you must execute its CREATE/ALTER batch against the correct database.

Teaching implementations: the following complete examples match the visible EmployeeService parameter and result contracts and the EF snapshot's column names. They were not exported from your SQL Server or executed for this document. Check your actual schema, procedure definitions, constraints, and triggers before using them. The scripts do not add email uniqueness, normalize emails, or define cascade behavior.

Your application's effective connection string must point to the same server and database that you inspect in SSMS.

GO is an SSMS/sqlcmd batch separator, not a SQL statement accepted by SqlCommand. Execute each CREATE OR ALTER PROCEDURE in its own batch. If deploying through migrationBuilder.Sql, omit GO and use separate migrationBuilder.Sql calls.

Step 2: email lookup for login

CREATE OR ALTER PROCEDURE [dbo].[GetEmployeeByEmail]
    @Email nvarchar(255)
AS
BEGIN
    SET NOCOUNT ON;

    SELECT Id, Name, Email, PhoneNumber, PasswordHash,
           Role, Salary, DepartmentId, ClientId
    FROM dbo.Employees
    WHERE Email = @Email;
END;
GO
  1. CREATE OR ALTER creates the named object or replaces its existing definition.
  2. @Email is an input parameter. Its name corresponds to the anonymous Email property in GetByEmail.
  3. SET NOCOUNT ON suppresses row-count messages; it does not suppress the SELECT result.
  4. The explicit column list makes the returned data contract visible.
  5. WHERE compares each row's email with the supplied value. Matching and case sensitivity depend on database collation; no normalization is implemented here.
  6. No matching row becomes null in C#, which the login action translates into 401.

No password is supplied to this SQL procedure. It retrieves the saved hash, and ASP.NET Core verifies the supplied password in C#. The query returns all matching rows; QueryFirstOrDefault takes the first. The inspected EF model has no unique Email index, so duplicate prevention remains a separate implementation concern.

Step 3: list employees

CREATE OR ALTER PROCEDURE [dbo].[GetAllEmployees]
AS
BEGIN
    SET NOCOUNT ON;

    SELECT Id, Name, Email, PhoneNumber, PasswordHash,
           Role, Salary, DepartmentId, ClientId
    FROM dbo.Employees
    ORDER BY Id DESC;
END;
GO

This procedure has no input parameters because the current service has no paging or filter arguments. ORDER BY makes the example's ordering explicit. Without an ORDER BY, SQL Server does not promise insertion order. QueryAsync returns the rows and ToList turns them into the interface's required list type.

PasswordHash is returned internally in this teaching example to keep the Employee shape consistent. The entity's JsonIgnore prevents its JSON serialization. A future public list response DTO could select only the fields that clients need and avoid retrieving password hashes for list requests altogether.

Step 5: create an employee

CREATE OR ALTER PROCEDURE [dbo].[CreateEmployee]
    @Name nvarchar(150),
    @Email nvarchar(255),
    @PhoneNumber nvarchar(10),
    @PasswordHash nvarchar(max),
    @Role nvarchar(50),
    @Salary decimal(18, 2),
    @DepartmentId int,
    @ClientId int = NULL
AS
BEGIN
    SET NOCOUNT ON;

    INSERT INTO dbo.Employees
        (Name, Email, PhoneNumber, PasswordHash, Role,
         Salary, DepartmentId, ClientId)
    VALUES
        (@Name, @Email, COALESCE(@PhoneNumber, N''),
         @PasswordHash, @Role, @Salary,
         @DepartmentId, @ClientId);

    DECLARE @NewId int = CONVERT(int, SCOPE_IDENTITY());

    SELECT Id, Name, Email, PhoneNumber, PasswordHash,
           Role, Salary, DepartmentId, ClientId
    FROM dbo.Employees
    WHERE Id = @NewId;
END;
GO
  1. Each parameter matches a property in EmployeeService.Create's anonymous object. The procedure accepts a hash, not a plaintext password.
  2. The parameter lengths mirror the current API profile limits. They are teaching choices, not proof that the deployed table uses the same lengths. Role currently lacks a matching API length/allowlist constraint.
  3. @ClientId defaults to NULL because a client is optional. @DepartmentId is required and should refer to an existing department.
  4. The INSERT omits Id so SQL Server generates it through the identity column.
  5. COALESCE substitutes an empty string for a null phone number. This handles the visible mismatch between nullable request PhoneNumber and the snapshot's non-null database column.
  6. SCOPE_IDENTITY returns the most recent identity produced in this scope. CONVERT changes its SQL numeric type to the int used by the model.
  7. The final SELECT returns the inserted employee. Without it, QuerySingleAsync cannot obtain the required result row.

This minimal example assumes ordinary table behavior without custom triggers changing or removing the inserted row. For more complex procedures, design transaction boundaries and result capture deliberately. A stored procedure does not automatically make a multi-statement operation one transaction.

Step 6: update an employee

CREATE OR ALTER PROCEDURE [dbo].[UpdateEmployee]
    @Id int,
    @Name nvarchar(150),
    @Email nvarchar(255),
    @PhoneNumber nvarchar(10),
    @PasswordHash nvarchar(max),
    @Role nvarchar(50),
    @Salary decimal(18, 2),
    @DepartmentId int,
    @ClientId int = NULL
AS
BEGIN
    SET NOCOUNT ON;

    UPDATE dbo.Employees
    SET Name = @Name,
        Email = @Email,
        PhoneNumber = COALESCE(@PhoneNumber, N''),
        PasswordHash = @PasswordHash,
        Role = @Role,
        Salary = @Salary,
        DepartmentId = @DepartmentId,
        ClientId = @ClientId
    WHERE Id = @Id;

    SELECT Id, Name, Email, PhoneNumber, PasswordHash,
           Role, Salary, DepartmentId, ClientId
    FROM dbo.Employees
    WHERE Id = @Id;
END;
GO

UPDATE assigns values to the row selected by Id. Omitting WHERE would change every employee, which is why the identifier condition is central to this operation. The final SELECT supplies the result EmployeeService expects; if the employee is absent, it returns no row.

This procedure accepts new Role and PasswordHash values, but the current controller sends the old values. SQL cannot decide that an unused model.Password should have been hashed; responsibility for that mapping is in C#.

Another request can change the row between statements. This example has no optimistic concurrency token or transaction protecting the entire read/update workflow. If concurrency guarantees are required, design the controller contract and SQL procedure together.

Step 7: delete an employee

CREATE OR ALTER PROCEDURE [dbo].[DeleteEmployee]
    @Id int
AS
BEGIN
    SET NOCOUNT ON;

    DELETE FROM dbo.Employees
    WHERE Id = @Id;

    SELECT @@ROWCOUNT AS AffectedRows;
END;
GO

DELETE removes the matching row. @@ROWCOUNT gives the affected-row count from the immediately preceding statement. SELECT exposes it as a result value for ExecuteScalarAsync<int>. Do not insert another statement between DELETE and this SELECT, because that can change @@ROWCOUNT.

A selected value of 1 becomes true in the service, and then HTTP 204. A selected 0 becomes false and 404. A foreign-key violation or another SQL exception is neither result; it throws. Decide deliberately how assigned tasks should behave when an employee is deleted.

Password hashing explained

PasswordHasher<Employee> is ASP.NET Core Identity's password helper. Its default IdentityV3 format uses PBKDF2 with a random salt and stores a versioned representation containing the information needed to verify it. The project constructs the helper with defaults; it does not configure its own hashing algorithm or work factor.

The employee object argument is part of the helper's API. The default implementation does not derive the hash from the employee name, ID, or role. The supplied password is the value being hashed. The output is encoded for storage; encoding a password with Base64 alone would not provide equivalent protection. See the ASP.NET Core PasswordHasher implementation.

var hasher = new PasswordHasher<EmployeeEntity>();
employee.PasswordHash = hasher.HashPassword(employee, model.Password);

var result = hasher.VerifyHashedPassword(
    employee,
    employee.PasswordHash,
    request.Password);

Do not hash the candidate password again and compare strings: fresh salts normally produce different outputs even for the same password. Use VerifyHashedPassword. SQL HASHBYTES produces a different format and is not a substitute for this API. Existing employees with an empty or invalid hash need a proper credential setup/reset flow; adding a database column does not create usable passwords.

CreateToken, statement by statement

  1. Read Jwt:Secret. If the configuration entry is absent, throw a configuration error.
  2. Read issuer and audience. These identify the expected token issuer and intended recipient. Program validates the same values.
  3. Read ExpirationMinutes with a fallback of 30 and compute an expiry from DateTime.UtcNow.
  4. Create the claim list. Sub identifies the subject, Jti gives the token a unique ID, Name provides an identity name, and Role carries Manager or Employee (or whatever stored value was passed).
  5. If employeeId has a value, add a NameIdentifier claim. The configured ApiUser branch has no employee ID because it did not load an employee record.
  6. Convert the secret to UTF-8 bytes and construct a SymmetricSecurityKey.
  7. Create SigningCredentials with HmacSha256. Signing lets the receiver detect modification; it does not encrypt the payload.
  8. Construct JwtSecurityToken with issuer, audience, claims, expiry, and signing credentials.
  9. WriteToken serializes it into the compact bearer-token string.
  10. Return Token and ExpiresAt in LoginResponseViewModel.

A JWT contains claims that a holder can decode. Do not put passwords or SMTP secrets in it. Possession of a valid token allows its use until it expires or the server rejects it for another reason, so protect it in transit and storage.

Roles are captured when a token is issued. Changing a database role or deleting an employee does not automatically revoke an already issued JWT in the current implementation. Program validates the token, but there is no per-request database role refresh or token revocation check.

10. Manager and Employee Access

Authentication establishes identity from a valid token. Authorization checks whether that identity satisfies an endpoint's requirements. A username containing the word admin has no special effect. Role attributes inspect role claims, not the text of the login name.

[Authorize(Roles = "Manager")]
// Only the Manager role meets this requirement.

[Authorize(Roles = "Manager,Employee")]
// Either listed role meets this single requirement.

A role attribute on the controller applies to its actions. Additional authorization attributes on an action add requirements; they do not simply replace the controller requirement. The comma-separated role list is an OR within that attribute. See Microsoft's role authorization documentation.

  2. The class implements IEmployeeEmailSender, allowing it to be substituted wherever that interface is requested.
  3. The constructor receives IOptions<MailSettings> and saves options.Value, the bound settings object.
  4. The Enabled check exits without sending when email is disabled. The caller receives a completed Task; it is not told that delivery was skipped.
  5. using var message ensures MailMessage is disposed at method exit.
  6. From constructs the sender address and display name. Subject supplies the subject line.
  7. The interpolated raw string body inserts employee.Name, employee.Email, plainPassword, and employee.Role into readable text. Raw string syntax preserves a multi-line body without repeated newline escape sequences.

  10. SmtpClient uses the configured host and port; EnableSsl takes UseSsl; Credentials receives the provider username and password.
  11. SendMailAsync submits the message to the SMTP server. Exceptions propagate because this method has no catch.
  12. The using declarations dispose both network/message objects afterward.

Successful SMTP submission does not prove the email reached the inbox. The provider may accept it and later bounce or filter it. The code does not track delivery, queue retries, or expose a resend endpoint.

Step 5: configure a provider

  1. Obtain the SMTP hostname, STARTTLS port, authentication username, app password or SMTP credential, and permitted From address.
  2. Set the MailSettings values in configuration. Start with Enabled=false while testing unrelated database behavior.

Current credential-email limitation

The implemented message includes a plaintext application password and says to change it after login. There is currently no self-service change-password endpoint in these controllers, and the Manager update action ignores its optional password field. The email's instruction does not create that capability.

For a future production onboarding design, prefer a short-lived one-time account setup link so the employee chooses their password. This would require a token lifecycle and corresponding API/UI work. The current implementation is documented here as it exists; it does not provide that flow.

13. Migrations and Deployment

A migration is versioned code describing database changes. Creating a migration writes a file; applying it changes a database. Saving an Employee or calling a stored procedure is an ordinary data operation, not a migration.

The current startup initializer

Current source: EmployeeApi/Data/EmployeeApiDatabaseInitializer.cs. Original line numbers; comments omitted where applicable.

  1using Microsoft.EntityFrameworkCore;  2  3namespace EmployeeApi.Data;  4  5public static class EmployeeApiDatabaseInitializer  6{  7    public static async Task EnsureSchemaAsync(ApplicationDbContext dbContext)  8    {  9        await dbContext.Database.MigrateAsync(); 10    } 11} 12

Program creates a scope, resolves ApplicationDbContext, and awaits this method. MigrateAsync applies pending migrations to the configured database. Consequently, simply starting this backend can change the schema. If the database is unavailable or the SQL identity lacks migration permissions, startup can fail before requests are served.

A real schema-change migration

Up adds PasswordHash and Role columns to Employees. Both are non-null. The migration supplies an empty string for PasswordHash and Employee for Role when the columns are introduced. These values do not create a valid password for pre-existing employees. Down removes both columns, which would remove the corresponding stored data.

The Role initializer in Employee.cs is a C# default. The defaultValue in a migration is SQL schema/data behavior. They are separate mechanisms. Editing an already applied migration does not cause EF to rerun it against a database whose migration history already records it.

Login and navigation

After successful login, the frontend stores the returned token and decides where to navigate. The backend login endpoint returns JSON, not a redirect. A complete account-creation trace to explain aloud

A Manager submits JSON to POST /api/employee/new. JWT middleware validates the token, then authorization confirms Manager. ASP.NET binds and validates CreateEmployeeViewModel. The controller maps profile fields, hashes the supplied password, sets the role, and calls the service. Dapper sends named parameters to dbo.CreateEmployee. SQL inserts the row and selects it back with its new Id. Dapper maps that row into Employee. The controller invokes the email sender, which either exits when disabled or submits a message through SMTP. Finally, CreatedAtAction produces a 201 response with the employee JSON and a Location header. The frontend receives it and updates the displayed list or navigates according to its own logic.

A complete login trace to explain aloud

The employee enters their email into the login field and their password. The frontend sends username and password. AuthApiController first checks the configured ApiUser branch. Otherwise it passes username to GetByEmail, which calls the SQL procedure and returns the employee including PasswordHash and Role. The hasher verifies the candidate password. On success, CreateToken builds signed claims using the employee's email, role, and ID. The response gives the frontend a token and expiry. Later requests attach the token; middleware validates it and action attributes determine whether the requested operation is allowed.
